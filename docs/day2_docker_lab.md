# Day 2 Docker Traffic Lab

## Objective

Create an isolated Docker network with three containers:

- server: exposes HTTP, FTP and iperf3 services.
- client: generates legitimate traffic.
- attacker: generates anomalous or reconnaissance traffic.

## Network Design

The lab uses a custom Docker bridge network:

- Network: 172.20.0.0/24
- Gateway: 172.20.0.1
- server: 172.20.0.10
- client: 172.20.0.20
- attacker: 172.20.0.30

The network is isolated and controlled. This makes the generated traffic reproducible and avoids mixing it with private host traffic.

## Services

The server container runs:

- nginx on TCP port 80
- vsftpd on TCP port 21
- iperf3 on TCP port 5201

FTP credentials:

- user: ftpuser
- password: ftppass

These credentials are synthetic and only used inside the Docker lab.

## Verification Results

The following checks were completed successfully:

- The three containers are running.
- The client can reach the server.
- The attacker can reach the server.
- HTTP traffic works through nginx.
- FTP upload works through vsftpd.
- iperf3 generates sustained TCP traffic.
- nmap generates reconnaissance traffic.
- hping3 generates TCP SYN packets.
- A PCAP file was captured and opened in Wireshark.

## Useful Commands

Container status:

    docker compose ps

HTTP test:

    docker compose exec client curl -I http://server

FTP test:

    docker compose exec client bash -lc 'echo "FTP smoke test from client" > /tmp/ftp_test.txt && lftp -u ftpuser,ftppass -e "set ftp:ssl-allow no; set ftp:passive-mode on; put /tmp/ftp_test.txt -o upload/ftp_test.txt; ls upload; bye" ftp://server'

iperf3 test:

    docker compose exec client iperf3 -c server -t 5

nmap test:

    docker compose exec attacker nmap -sS -p 21,80,5201 server

hping3 test:

    docker compose exec attacker hping3 -S -c 5 -p 80 server

## Packet Capture

A reliable PCAP can be captured from the server container:

    docker compose exec -d server bash -lc 'tcpdump -i any -U -w /captures/day2_smoke.pcap'

After generating traffic, stop the capture with:

    docker compose exec server pkill tcpdump || true

The resulting PCAP is stored in:

    data/raw/day2/day2_smoke.pcap

Raw PCAP files are ignored by Git because they can be large and may contain sensitive traffic.

## Wireshark Evidence

The PCAP was opened in Wireshark and the following filters were verified:

    ip.addr == 172.20.0.10
    ftp or tcp.port == 21
    ip.src == 172.20.0.30 and tcp.flags.syn == 1 and tcp.flags.ack == 0

These filters confirm:

- General traffic involving the server container.
- FTP control traffic between the client and the server.
- SYN packets generated by the attacker container.

## Technical Decisions

### Custom Docker bridge network

A custom bridge network gives deterministic container-to-container communication, internal DNS resolution and stable IP addresses.

### Static IP addresses

Static IP addresses simplify Wireshark and TShark filtering. For example, all server traffic can be filtered with:

    ip.addr == 172.20.0.10

### Separate client and attacker containers

Separating legitimate and anomalous traffic sources makes future labeling easier. Traffic from 172.20.0.20 is normal, while traffic from 172.20.0.30 is attack or reconnaissance traffic.

### FTP support

FTP is included because it produces flows with different characteristics from HTTP. File transfers generate longer-lived and larger flows, which will later help feature engineering and classification.

### Capturing inside the server container

On Windows 11 with WSL2 and Docker Desktop, Wireshark may not always see internal Docker bridge traffic directly. Capturing from the server container with tcpdump and opening the resulting PCAP in Wireshark is a reliable alternative.

### PCAP privacy

Even in a synthetic environment, PCAP files may contain sensitive information. For example, FTP credentials are visible in clear text. Therefore, raw PCAP files are excluded from version control.
